# Bootstrap and verify

The default scope is a private GitHub repository on `main`, the committed template, Codex Cloud setup and four cloud checks. Hosted credentials and production branches are needed only when the person requests hosted setup. Read [hosted.md](references/hosted.md) for that branch.

1. Resolve the directory containing **this loaded SKILL.md**, following its installation symlink to the source checkout. Call it `SKILL`. Use absolute, quoted paths to `"$SKILL/scripts/tg"`; the helper is not on PATH. Its sibling `../assets/template` must remain accessible. Node >=22.23 is required. Discover or repair missing tools with the supported package manager before running TypeScript.
2. Never bootstrap the Touch Grass source checkout itself. From the target directory run `"$SKILL/scripts/tg" route --json`. A `bootstrap` result continues the global workflow below, including an interrupted bootstrap whose verifier arrived before GitHub publication. A `verify` result names the repository-local skill to read and execute instead of provisioning. This routing command reads the bootstrap receipt and creates nothing; its result is not verification evidence. In a cloud task, also capture the observed task/environment identity, repository origin and exact tested commit for the report. An explicit request to finish cloud setup can continue at step 5 after confirming the repository is published, even if the route is `verify`.
3. From the target directory run `"$SKILL/scripts/tg" status --json`, then `"$SKILL/scripts/tg" run --json`. These helpers use a private manifest and journal, preserve unrelated files, pin committed source blobs and bind the remote identity. Exit 2 means incomplete. Repair a named dependency/authentication problem, complete available `agent` actions, and rerun. Stop retrying a conflict or uncertain resource creation until its cause is resolved. Keep user files and the creation receipt intact. The helpers never install app dependencies locally or provision hosted services.
4. For authentication, use an existing authorized connector/CLI session first. Start the required vendor login when absent and drive its supported browser UI. Continue navigation, forms and configuration until the next action requires the person's account choice, password, OAuth/permission approval or billing decision. State that exact gate and resume after it completes. Never ask for credentials in chat. Tool-specific pickers and confirmations remain required.
5. Once GitHub is published, read [cloud.md](references/cloud.md). Complete its account and repository-access prerequisites before runtime setup. Discover supported Codex environment tools first; otherwise use the supported browser environment UI and setup conversation. Continue through installation, inspect the prepared private environment, and publish when needed to verify a fresh task. Publishing an intermediate checkpoint is not setup completion. CLI task submission applies only to a Legacy environment actually discoverable by that CLI. Use the cloud reference's runtime recipe, capability decisions and explicit `$touch-grass` handoff.
6. Observe the cloud task through completion when the supported surface permits it. Record each of repository access, frozen install, build and full check as `passed`, `failed` or `not run`. Stop each four-check attempt at its first failure as the local verifier requires. Diagnose and repair the cause, then restart all four checks. Persist until they pass or a concrete human-only gate remains after supported alternatives. Missing runtime capabilities and `pnpm check` exit 2 leave verification incomplete. Preserve failed attempts separately; do not substitute local results or CI. Repository source fixes belong in a coding task, followed by verification of the new commit.

The local helper deliberately keeps cloud actions pending because local state cannot attest a remote runtime. Close those actions in the conversation only from supported UI/task observations. An environment ID or submitted task is insufficient. Bind cloud results to the actual repository, tested commit and observed selected environment/task; a new HEAD needs new verification.

Report the repository URL, observed environment/task link or explicit handoff, and three independent states. **Provisioning** is configured or pending with a concrete gate. **Cloud verification** lists all four results and the tested revision. **Deployment** is not configured unless explicitly requested and independently observed. Claim setup complete only when all four checks passed in that cloud runtime. A handoff remains pending verification.
