# Optional hosted setup

Read this only after an explicit hosted-setup request. The default bootstrap creates none of these resources and collects no hosted keys. Read the generated repository's `SETUP.md` for its exact configuration and build-secret names. Discover connected account/project state and current API schemas first. Prefer authorized connectors, then official CLI/API, then accessible browser UI. The agent executes the available steps; a browser-only surface is not automatically a person task. Hand over only account/password/OAuth/permission, cost/organization choices, billing and user-authored legal content that require the person.

Keep a receipt of resource IDs and intended repository/environment bindings. Match IDs, not names alone. Store secret values only through a connector's approved destination or mode-0600 gitignored files/stdin/environment. Keep tokens and passwords out of argv, chat, journal, reports and raw subprocess error output. Suppress sensitive stdout/stderr on failure. Read explicitly selected OAuth downloads without deleting them. Delete only owned temporary files after a successful transfer. Review concrete config changes and observed cost before crossing a tool-required confirmation or deploy gate.

## Supabase first

Use the installed Supabase skill and connector. List organizations/projects and inspect organization billing/cost through supported tools. Ask for an organization or spending decision only when needed; do not assume two Free slots remain. Follow `get_cost`/`confirm_cost` if the connector exposes them. Auth can be existing OAuth or an authorized PAT, never a project key pretending to be a Management API token. The [CLI login docs](https://supabase.com/docs/reference/cli/supabase-login) require a token in noninteractive shells; use browser/token entry privately at that gate.

The [Management API schema](https://api.supabase.com/api/v1-json) describes `GET /v1/organizations`, `GET /v1/projects` and `POST /v1/projects` with `organization_slug`, `name`, private generated `db_pass`, and `region_selection` (`specific` code or `smartGroup`). Inspect current region availability and organization plan. Deprecated `plan` is ignored because billing is organization-level. Wait for `ACTIVE_HEALTHY`. Bind dev/production separately. A creation error is not proof of free capacity or permission to switch organizations.

Fetch suitable keys with `GET /v1/projects/{ref}/api-keys?reveal=true`; if needed `POST` creates a `publishable` or `secret` key. Secret reveal and creation need granted secret permissions. Transfer privately to the corresponding Worker. For `SUPABASE_DB_URL`, inspect `GET /v1/projects/{ref}/config/database/pooler`, select the returned **session** pooler and its actual host/port/user, and percent-encode the generated password. Do not invent the host from a region. [Management auth](https://supabase.com/docs/reference/api/introduction) supports PAT/OAuth; minting a PAT remains an account UI gate. The build PAT is a separate user-authorized credential. Never print pooler URLs containing passwords.

## Google OAuth

After both Supabase refs exist, automate the Google Cloud console to the available account gates. Create or explicitly reuse the Cloud project, configure Google Auth Platform branding/audience, and create a Web application client with exact `https://<ref>.supabase.co/auth/v1/callback` URIs for each project. Follow [Supabase's Google guide](https://supabase.com/docs/guides/auth/social-login/auth-google) for `openid`, email and profile scopes.

Production branding may require a homepage, privacy policy, Terms and authorized domains under [Google's requirements](https://support.google.com/cloud/answer/15549049). A free no-domain production path and suitability of `workers.dev` are unverified. Obtain the person's real legal content/domain choices when required; do not fabricate policies or publish invented consent text. [Verification guidance](https://support.google.com/cloud/answer/13463073) exempts only non-sensitive-scope apps from verification; that does not establish that branding is optional. Capture the client secret privately when shown, per [client guidance](https://support.google.com/cloud/answer/15549257), or read an explicitly selected JSON download. Transfer client ID/secret to the build settings through the authorized API/private channel. Do not infer a newest Downloads file or erase it.

## LLM keys

For OpenAI key creation or use, load installed `openai-developers:openai-platform-api-key` and follow its connector picker plus local-destination confirmation. Use a gitignored destination with the requested `LLM_API_KEY` name and transfer to the corresponding Worker privately. Do not build an admin-key bypass or ask for a key in chat. The person owns billing and spend choices. Other providers need their own supported auth/limits workflow and explicit provider choice.

## Cloudflare and Workers Builds

Use the installed Cloudflare skill and discover connector/CLI permissions. Read accounts/subdomain/resources before choosing IDs. Prepare `wrangler.jsonc` and `supabase/config.toml` with observed refs/URLs, per-environment UUIDs and the person's provider configuration. Run the repository's placeholder/repository checks on those changes. Keep production branch creation and release out of default bootstrap.

The [Builds API guide](https://developers.cloudflare.com/workers/ci-cd/builds/api-reference/) requires a **user-scoped** token with **Workers Builds Configuration: Edit**. Add **Workers Scripts: Read** only if listing Worker tags. An account-scoped token is rejected. Wrangler OAuth scopes do not establish Builds permission. The Cloudflare GitHub App must first be installed through the dashboard; drive that browser flow to its permission approval and resume afterward. A Builds API token differs from the build token UUID used to deploy.

After that one-time gate, automate the supported API sequence. Inspect current schemas, then get GitHub owner/repo IDs, upsert `PUT /accounts/{id}/builds/repos/connections` with provider type/account/name/repo identity, obtain the existing Worker tag from `GET /workers/scripts`, and list/create build-token UUIDs through `/builds/tokens`. `POST /builds/triggers` uses `external_script_id` (Worker **tag**), connection UUID, build-token UUID, commands and branch filters. Use one Worker for dev/main and one for production/production. Inspect preview settings; branch filters alone do not prove preview builds disabled. See [connections](https://developers.cloudflare.com/api/resources/workers_builds/subresources/repos/subresources/connections/methods/upsert/), [triggers](https://developers.cloudflare.com/api/resources/workers_builds/subresources/triggers/methods/create/) and [build tokens](https://developers.cloudflare.com/api/resources/workers_builds/subresources/tokens/methods/create/).

Configure build variables/secrets with `PATCH /accounts/{id}/builds/triggers/{uuid}/environment_variables`, using `{name: {is_secret, value}}`, from a private process/connector payload. Secret values read back null. Set `CLOUDFLARE_ENV`, `PNPM_VERSION` and the exact build secrets from `SETUP.md`. [Variables API](https://developers.cloudflare.com/api/resources/workers_builds/subresources/triggers/subresources/environment_variables/methods/upsert/) supports this; handing every paste to the person is unnecessary when authorized tools can transfer privately. Runtime secrets can use `wrangler secret put` on stdin for the observed Worker name.

Creating a Worker/trigger, connecting a repository, enabling Builds, pushing a production branch or requesting a first build may deploy. Prepare all safe configuration first and obtain explicit deployment authorization immediately before a deploy-triggering action, unless the person already granted that exact scope. A verified disabled/draft mode may be used only when the actual API supports it. Observe build status/logs with `/builds/workers/{tag}/builds` and `/builds/builds/{uuid}` after an authorized trigger. Successful build is not deployed-app verification; run the repository's `verify:deployed` flow with private secret input. Report hosted provisioning, cloud development verification and deployment verification separately.
